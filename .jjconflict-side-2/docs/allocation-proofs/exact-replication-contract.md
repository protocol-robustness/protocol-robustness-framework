# Exact replication contract

This document records the byte-for-byte compatibility contract between the PRF
reference allocation kernel and the independent native Rust kernel. It is the
foundation of `:comparison/scope :exact-replication`.

## Gate

```
PRF public result == native Rust public result
```

The gate is enforced by `scripts/conformance/conformance.sh`: the pinned PRF JAR generates
the conformance vector suite, and the native kernel must reproduce every
expected public value (passing vectors) and every rejection classification
(failing vectors). Missing or extra fields are failures.

## Canonical ABI

Both implementations use `CANONICAL_HASH_SPEC_V1_BINARY_ENCODING_ABI`:

- `NULL` 0x00, `BOOL_FALSE` 0x01, `BOOL_TRUE` 0x02
- `INT` 0x10 = varuint(zigzag(n))
- `STRING` 0x20 = varuint(len) || UTF-8
- `KEYWORD` 0x22 = varuint(len) || "ns/name" or "name"
- `ARRAY` 0x30 = varuint(count) || concat(elements)
- `MAP` 0x31 = varuint(count) || concat(pairs sorted by encoded key bytes)

varuint is LEB128 little-endian base-128, minimal representation. Maps sort
keys by their encoded bytes. No Rust-specific encoding is used.

The Rust port lives in `coprocessor/core/src/canonical.rs`, with golden
byte-preimage tests in `tests/canonical_golden.rs` generated from the PRF JAR.

## Selection algorithm

`:domain-hash-rejection-v1`:

1. n = number of canonically ordered outcomes; require n > 0.
2. For counters from 0:
   `candidate = SHA256(SELECTED_OUTCOME_V1 || canonical_bytes({:authoritative-randomness <32 bytes> :counter c :outcome-count n}))`
3. Interpret the digest as an unsigned big-endian integer.
4. M = 2^256; limit = M - (M mod n).
5. If candidate < limit, selected-index = candidate mod n; else increment c.
6. Return the outcome at selected-index in canonical outcome order.

## Public-value projection

Both implementations emit exactly these fields (no more, no fewer for the
conformance comparison):

```
result/status
allocation-context-hash
claimant-set-root
outcome-set-root
proposed-rates-root
rate-derived-summary-hash
assertions (ordered 14)
selection-receipt
selected-outcome-id
selected-outcome-index
selected-outcome-hash
result-root
total-allocated
residual-capacity
certificate-assertions-digest
allocation-kernel-version
selection-algorithm
(+ rejection/classification when rejected)
```

`rejection/reason` is a diagnostic and is not part of the projection.

## The 14 assertions

In order:

1. `allocation.assertion/claimant-set-root-valid`
2. `allocation.assertion/outcome-set-root-valid`
3. `allocation.assertion/proposed-rates-root-valid`
4. `allocation.assertion/rates-canonical-exact`
5. `allocation.assertion/rates-sum-to-one`
6. `allocation.assertion/outcomes-eligible-only`
7. `allocation.assertion/outcomes-no-duplicate-claims`
8. `allocation.assertion/outcomes-all-or-nothing`
9. `allocation.assertion/outcomes-exact-capacity`
10. `allocation.assertion/proportional-proposed`
11. `allocation.assertion/randomness-selection-valid`
12. `allocation.assertion/selected-outcome-membership`
13. `allocation.assertion/result-root-valid`
14. `allocation.assertion/result-capacity-reconciles`

Assertion 10 checks, for every claimant: `E-num_i * W = C * w_i * D` where
E-num_i is the expected-allocation numerator under the common rate denominator
D, W is total eligible weight, C is capacity, and w_i is claimant weight.
Assertion 14 requires `total-allocated == capacity` and `residual-capacity == 0`.

## Conformance vector suite (14 vectors)

The suite is generated by the PRF JAR (`allocation vectors`). The native Rust
kernel must reproduce every expected public value exactly.

| # | vector_id | expected status | rejection classification |
|---|-----------|-----------------|--------------------------|
| 1 | `a-vs-b-plus-c-happy-path` | passing | — |
| 2 | `a-vs-b-plus-c-claimant-order-permutation` | passing | — |
| 3 | `a-vs-b-plus-c-outcome-order-permutation` | passing | — |
| 4 | `a-vs-b-plus-c-malformed-rate-total` | rejected | `rates-not-sum-to-one` |
| 5 | `a-vs-b-plus-c-non-reduced-ratio` | rejected | `rates-not-canonical` |
| 6 | `a-vs-b-plus-c-partial-claimant-allocation` | rejected | `allocation-not-all-or-nothing` |
| 7 | `a-vs-b-plus-c-over-capacity-outcome` | rejected | `outcome-not-exact-capacity` |
| 8 | `a-vs-b-plus-c-under-capacity-outcome` | rejected | `outcome-not-exact-capacity` |
| 9 | `a-vs-b-plus-c-ineligible-claimant` | rejected | `ineligible-claimant` |
| 10 | `a-vs-b-plus-c-duplicate-claim-in-outcome` | rejected | `duplicate-claim-in-outcome` |
| 11 | `a-vs-b-plus-c-proportionality-failure` | rejected | `proportionality-failure` |
| 12 | `a-vs-b-plus-c-changed-authoritative-randomness` | rejected | `selected-outcome-mismatch` |
| 13 | `a-vs-b-plus-c-forged-expected-root` | rejected | `claimant-set-root-mismatch` |
| 14 | `a-vs-b-plus-c-empty-outcome-set` | rejected | `empty-outcome-set` |

Notes:

- 3 passing vectors, 11 rejected vectors.
- Vectors 7 and 8 intentionally share the classification
  `outcome-not-exact-capacity`: over-capacity and under-capacity both violate
  assertion 9 (`outcomes-exact-capacity`). Ten distinct classifications across
  eleven rejected vectors.

## Exact-replication scope

The conformance result may be classified `:comparison/scope :exact-replication`
only when both executions use the same identity-defining inputs: vector input
bytes (or semantically identical parsed input), claimant identities and
ordering, outcomes and ordering, exact rates, capacity, exact pro-rata
denominator, policy, authoritative randomness, selection algorithm, canonical
ABI version, kernel assertion contract, and result-leaf projection. If any
identity-defining field differs, the gate fails rather than downgrading.
